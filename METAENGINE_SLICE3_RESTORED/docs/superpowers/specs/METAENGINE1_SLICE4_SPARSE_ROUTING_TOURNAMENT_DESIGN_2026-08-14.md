## 1. Purpose

Slice 4 is the first clean-room causal mechanism experiment in METAENGINE-1. Its purpose is not to copy mixture-of-experts implementation code from an external model. It asks a narrower system-level question:

> When a task requirement is already characterized, does activating only a bounded capability-matched subset of specialists improve quality/efficiency under a frozen, equal processing-resource budget compared with dense activation and random top-k routing?

The stage MUST produce valid scientific evidence even if the answer is negative or null.

No result in this stage automatically grants mechanism assimilation, canonical promotion, active-policy mutation, Role Genome mutation, D6-G1 adaptation, or executable self-modification.

## 4. Alternatives considered

### 4.1 Legacy 16X `CapabilityRouter`

**Rejected as the primary experiment implementation.**

Advantages:
- lower implementation cost;
- existing routing semantics and tests.

Disadvantages:
- carries legacy capability registry assumptions, thresholds, and 16X scoring semantics;
- makes causal attribution ambiguous;
- risks measuring old system behavior rather than the mechanism itself.

It may be used later as an external comparison, not as the causal reference implementation.

### 4.2 Clean-room deterministic causal tournament

**Selected.**

Advantages:
- isolates sparse conditional routing from model/provider quality;
- supports frozen seeds and exact replay;
- uses `ResourceDescriptor` and `OrganizationPolicy` directly;
- allows a clear ablation among dense, random top-k, and capability-routed top-k;
- minimizes new dependencies and complexity.

### 4.3 Immediate heterogeneous live-model tournament

**Deferred to transfer testing.**

Advantages:
- higher ecological validity.

Disadvantages:
- provider/model quality, latency, stochastic sampling, API budget, and tool variability become confounders;
- weaker first-pass causal attribution.

A later heterogeneous transfer test is required before any assimilation claim.

## 5. Experiment topology

The experiment uses a frozen specialist pool described through provider-neutral `ResourceDescriptor` objects. A reference configuration SHOULD contain six deterministic specialists with deliberately overlapping but non-identical capability sets.

Each specialist consumes a deterministic portion of a fixed processing-resource budget when activated.

No specialist has access to hidden expected scores or evaluator internals.

### 5.1 Required arms

The experiment MUST compare exactly these causal arms:

1. `DENSE_ALL_SPECIALISTS`
2. `RANDOM_TOP_K`
3. `CAPABILITY_ROUTED_TOP_K`

For `RANDOM_TOP_K` and `CAPABILITY_ROUTED_TOP_K`, the first experiment uses `k = 2`.

`DENSE_ALL_SPECIALISTS` does not receive a larger processing-resource budget merely because more resources are active. The fixed budget is divided across active resources. This isolates organization from raw compute increase.

### 5.2 Equal processing-resource budget

The frozen baseline budget is:

`processing_resource_units = 2`

All arms receive the same total processing-resource units per task.

The experiment records organizational overhead separately from the equal processing budget, including:

- active resource count;
- routing/selection overhead;
- activation overhead;
- deterministic total-cost proxy;
- complexity delta.

---

## 6. Required task regimes

### 6.1 `REGIME_A_SEPARABLE_SPECIALIST_TASKS`

Task requirements map cleanly to distinct specialist capability subsets.

Hypothesis:

> Capability-routed top-k concentrates the fixed processing budget on relevant specialists and should outperform random top-k and budget-diluted dense activation.

### 6.2 `REGIME_B_AMBIGUOUS_OR_OVERLAPPING_TASKS`

Task requirements overlap or do not cleanly distinguish specialist subsets.

Purpose:
- act as an adversarial regime;
- detect overgeneralization;
- distinguish a contextual mechanism from a universal mechanism.

If sparse routing succeeds in Regime A but not Regime B, the correct local interpretation is contextual support, not universal support.

## 8. Routing semantics

### 8.1 Dense arm

`DENSE_ALL_SPECIALISTS` activates the full specialist pool but divides the same frozen processing-resource budget across all activated specialists.

### 8.2 Random arm

`RANDOM_TOP_K` selects exactly `k = 2` specialists using only a frozen seed and the frozen specialist list.

It MUST NOT access task-quality labels or evaluator outputs.

Multiple frozen seeds MUST be used to avoid interpreting one lucky random selection as a mechanism effect.

### 8.3 Capability-routed arm

`CAPABILITY_ROUTED_TOP_K` receives only declared task capability requirements and the public capability declarations in `ResourceDescriptor`.

It selects exactly `k = 2` resources using a deterministic ranking rule. Tie-breaking MUST be canonical and replayable.

The router MUST NOT access:
- expected task score;
- evaluator outputs;
- hidden task labels;
- post-hoc result information.

This stage intentionally does not test task-understanding quality. It isolates the conditional-activation mechanism after task requirements have already been characterized.

---

## 9. Evaluation model

The first Slice 4 experiment is deterministic and provider-neutral.

Each specialist produces a deterministic contribution based on the task and its declared capability relationship. The evaluator computes task quality from those frozen contributions under the arm's allocated processing budget.

The scoring model MUST be simple enough to audit and MUST NOT embed the desired winner by construction. At minimum, the test suite must include tasks where:

- one capability is strongly relevant;
- two capabilities are jointly relevant;
- capability overlap creates ambiguity;
- irrelevant specialists can dilute dense budget;
- random top-k may occasionally match the correct specialists;
- capability routing can make a wrong selection in the adversarial regime.

The experiment SHOULD include explicit counterexamples that can falsify the mechanism.

---

## 10. Required metrics

For each task, regime, arm, and random seed where applicable, record at least:

- `task_quality`;
- `active_resource_count`;
- `processing_resource_units`;
- `routing_error_rate`;
- `routing_overhead`;
- `activation_overhead`;
- `deterministic_cost_proxy`;
- `complexity_delta`;
- reproducibility identity/hash.

Aggregate results MUST preserve per-regime and per-arm values. A single aggregate score is insufficient for the decision.

---

## 11. Required ablation comparisons

The stage MUST preserve direct comparisons among:

- dense activation;
- random top-k;
- capability-routed top-k.

The causal question is not merely whether routed execution scores well. It is whether capability-informed sparse selection explains an effect beyond:

- activating every specialist;
- activating an equally sized random subset;
- receiving more compute.

No arm may silently receive a larger processing-resource budget.

---

## 12. Decision semantics

The only allowed local scientific decisions are:

### `FALSIFIED_LOCAL`

Evidence does not support the hypothesized routing effect in the frozen local experiment, or capability routing is not meaningfully better than relevant baselines under the decision contract.

### `CONTEXTUAL_LOCAL`

The mechanism is supported in at least one preregistered regime but fails or becomes non-beneficial in another, establishing a task-region boundary.

### `SUPPORTED_LOCAL`

The mechanism demonstrates the preregistered local causal effect across the required regimes and passes the frozen regression/resource criteria.

These outcomes describe the local experiment only.

None of them authorizes automatic mechanism assimilation.

## 17. Error handling and fail-closed behavior

The experiment MUST fail closed when:

- a required resource descriptor is missing or has a mismatched hash;
- a task references an unknown capability/resource;
- an arm exceeds the frozen processing budget;
- random routing uses an unregistered seed;
- contract hash or mechanism card hash is stale;
- evaluator contract differs after execution begins;
- result receipt does not match recomputed identity;
- a requested interpretation attempts to exceed the allowed local decision classes;
- any code path attempts canonical mutation as part of the experiment.

Errors MUST use stable codes suitable for deterministic tests.
